# 性能实测（真实目录，2026-09-11）

> 所有数字都是在本机对**真实目录** `D:\TestData` 实测得到，不是估算。
> 目的：用数据决定"保护一个大目录到底该怎么做"，而不是凭感觉。

---

## 1. 被测对象

| 项 | 值 |
|---|---|
| 目录 | `D:\TestData` |
| 文件数 | **389,016** 个 |
| 目录数 | **7,271** 个 |
| 总大小 | **43.6 GB** |
| 跳过（排除规则） | 58 个 |
| 纯枚举耗时 | **13.6 秒**（`throttleEvery=3000` 时 `Throttled=True`） |

---

## 2. 三种保护模式的实测对比（各取前 3000 条）

| 模式 | 耗时 | 吞吐 | 内容对象 | 实际占用 | 峰值内存 |
|---|---|---|---|---|---|
| 只记录变化 | **0.7 秒** | **4,164 条/秒** | 0 | 0 | 8 MB |
| 智能留存（阈值 4MB） | 31.2 秒 | 96 文件/秒 | 2,960 | 10.1 MB | 5 MB |
| 完整内容 | 23.8 秒 | 126 文件/秒 | 2,961 | 15.1 MB | 5 MB |

**推算全量 39.6 万条**：只记录变化 ≈ **2 分钟**；留存内容 ≈ **50~70 分钟**。

---

## 3. 瓶颈定位：不是 CPU，不是内存，是 fsync

实测发现"留存内容"的吞吐（约 100~130 个/秒）几乎正好等于
**每秒能完成的磁盘 fsync 次数**。原因：

1. 内容对象要写 `objects.db`（`synchronous=FULL` → 每次提交 fsync ×1）；
2. 事件与索引要写 `events.db`（再次 fsync ×1）；
3. 内容字节本身还要落盘（`WriteThrough`）。

验证过的两个"优化"及其结论：

| 尝试 | 结果 |
|---|---|
| 把整趟扫描包进一个大事务 | **无改善**（两个库各自的提交仍在 fsync），且取消时事务回滚反而丢结果 → **已放弃** |
| `PRAGMA synchronous=OFF` 临时灌入 | 无改善（瓶颈是对象文件写入的 WriteThrough，不只是 SQLite）→ **未采用** |

**结论：这是机械盘的物理极限，不该靠牺牲持久性去"优化"。**
正确做法是**把选择权交给用户**（三档保护模式），并**提前如实告知代价**。

---

## 4. 为什么这些改造是必要的（用户实际遭遇）

用户在 `D:\TestData`（39 万文件）上点「添加保护」时：

| 问题 | 根因 | 后果 |
|---|---|---|
| 界面**未响应** | 基线扫描跑在 UI 线程上 | 用户只能强杀进程 |
| 强杀后时间线**永远空白** | 基线未建立 → 监听从未启动 → 事件数为 0 | 用户以为程序坏了 |
| **撤销按钮永远灰的** | 没有任何恢复记录 | 用户以为功能没做 |
| 出现了两个"只含 208 个文件"的恢复点 | 扫描未完成时点了「创建恢复点」 | 恢复到它会"删掉"1.7 万个文件 |

改造后的对应行为：

1. 添加目录**瞬间返回**（登记 + 开监听），扫描放后台；
2. 扫描前先**评估规模**并把耗时/占用/能力写在对话框里，让用户决定；
3. 进度条显示"已处理 N/M（x%）"，**随时可取消**，取消后已扫描部分有效、可续扫；
4. 基线未建立时设置页显著提示并提供「重新扫描补齐」；
5. 内容不完整的恢复点被标记并说明原因，「删除选中恢复点」可直接清理。

---

## 5. 单趟流式改造（消除 3 遍枚举）

改造前后端基线扫描的枚举次数：

| 版本 | 枚举次数 | 说明 |
|---|---|---|
| 改造前 | **3 遍** | ①统计 ②把全部条目收集进 `List` ③逐条比对写索引 |
| 改造后 | **1 遍** | 流式处理 + 每 200 条批量提交索引 + 每 2000 条批量写事件 |

副作用：峰值内存从"随目录规模增长"降到 **5~8 MB**（39 万文件规模下）。

## 6. 如何复现

本项目内的基准工具在验证后已删除（避免交付物膨胀）。如需复现：

1. 复用 `Rescanner.Estimate(path, mode, smartMaxBytes)` 做规模评估（只枚举、不读内容）；
2. 用 `Rescanner.Align(root, ResyncMode.Baseline, progress, cts.Token)` 跑真实基线，
   进度回调里打印 `p.Processed / p.Files / p.Bytes` 与 `GC.GetTotalMemory`；
3. 保护模式由 `AppSettings.Protection` 控制，阈值 `AppSettings.SmartContentMaxBytes`。

`ScanEstimate` 里固化的两个实测吞吐常量：

```csharp
public const double ContentFilesPerSecond = 110.0;      // 留存内容
public const double NoContentEntriesPerSecond = 3500.0; // 不留存内容
```

界面上的"预计首次扫描耗时"就是按这两个常量算的 —— 宁可估保守一点，
也不要让用户以为"很快就好"。
