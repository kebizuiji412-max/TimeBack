# 数据库设计说明

> 对应代码：`code/src/LastRegret.Windows/Sqlite/Schema.cs`
> 设计目标：**增量存储 + 可独立恢复 + 崩溃安全 + 查询不做全表扫描**

---

## 1. 为什么拆成两个数据库

| 库 | 内容 | 理由 |
|---|---|---|
| `events.db` | 事件、路径索引、快照与清单、版本、恢复记录、进程、设置 | 访问频繁、体积可控；查询要快 |
| `objects.db` | 内容对象索引（`objects` 表） | 体积可能很大；可独立备份 / 清理 / 校验；与业务表解耦 |

真实字节存放在文件系统的 `store/objects/<前两位>/<SHA-256>`，两个库都只存索引与引用。

---

## 2. 表清单与职责

| 表 | 职责 | 关键点 |
|---|---|---|
| `meta` | 键值元信息 | 存 `schema_version`、创建时间、应用版本；**结构升级的依据** |
| `watched_roots` | 受保护目录 | `path_key` 小写形式做大小写不敏感唯一约束；含排除规则、单文件上限、基线快照 Id |
| `files` | **路径索引（当前状态）** | 系统状态中枢：事件处理器据此判定 创建/修改/重命名；快照据此增量构建；恢复预览据此与目标清单对比。`WITHOUT ROWID` + 复合主键 `(root_id, path_key)` |
| `events` | **事件日志（历史事实）** | 时间统一用 UTC ticks（可排序可索引），另存落库时的本地时间避免事后时区漂移；含前后哈希/大小/对象 Id/合并计数/来源/关联进程 |
| `file_versions` | 文件历史版本 | 同一内容不重复登记；与事件、快照双向可追溯 |
| `snapshots` | 恢复点元数据 | 含 `event_high_watermark`（时间线定位）与统计字段 |
| `snapshot_files` | **快照清单（完整状态）** | 每行是"某路径在某时刻的状态"；因此快照**不依赖事件日志**即可恢复 |
| `restore_operations` | 恢复操作 | 目标时间、目标/安全/后置快照、状态、计划指纹、撤销关系 |
| `restore_steps` | 恢复明细（= 执行日志） | 每步的执行前内容引用；**崩溃后据此判断实际做到哪一步** |
| `processes` | 关联进程 | 只记录"附近出现过什么"，不表达因果 |
| `settings` | 设置键值 | JSON 主体 + 单键读写 |
| `_manifest_stage` | **会话级临时表** | 快照清单批量写入的中转站；不落盘、不产生 WAL |

## 3. 索引设计（每个查询路径都有对应索引）

| 索引 | 服务的查询 |
|---|---|
| `ux_watched_roots_path` | 按路径查根（大小写不敏感） |
| `ix_files_live` / `ix_files_changed` / `ix_files_hash` | 列出存活条目 / 按时间排序 / 按内容查路径 |
| `ix_events_time` | 时间线（按根 + 时间倒序） |
| `ix_events_path_time` | 某文件的全部历史事件 |
| `ix_events_op_time` | 按操作类型过滤（例如只看删除） |
| `ix_events_visible` | 时间线默认视图（排除瞬时事件） |
| `ix_events_pid` | 按关联进程过滤（部分索引，仅非空行） |
| `ix_versions_path` / `ix_versions_time` / `ix_versions_obj` | 文件历史 / 清理 / 对象反查 |
| `ix_snapshots_root_time` / `ix_snapshots_kind` | 恢复点列表 / 找最近一次安全点 |
| `ix_snapfiles_path` / `ix_snapfiles_object` / `ix_snapfiles_hash` | 某路径在历史快照中的状态 / **清理保护名单** |
| `ix_restore_root_time` / `ix_restore_status` | 恢复历史 / 找可撤销操作 |
| `ix_restore_steps_op` | 某次恢复的逐步账目 |
| `ux_objects_hash` | 内容去重命中的唯一约束 |

## 4. 崩溃安全

| 手段 | 做法 |
|---|---|
| 日志模式 | `journal_mode=WAL`：崩溃后可用 WAL 恢复，读写不互相阻塞 |
| 提交持久性 | `synchronous=FULL`：每次提交都 fsync。历史数据库宁可慢，也**绝不能**出现"已提交但断电后丢失" |
| 引用完整性 | `foreign_keys=ON` + 外键全部显式声明；删除根目录时级联清理其历史 |
| 写入原子性 | 内容对象写入 = 临时文件 → fsync → **校验哈希** → 原子改名；断电最坏只留下临时文件 |
| 事务边界 | 所有多行写入都在 `BEGIN IMMEDIATE` 事务内；失败自动回滚；提交遇 BUSY 自动重试 |
| 启动自检 | `PRAGMA integrity_check` + `PRAGMA foreign_key_check`，发现问题**如实报告**而不是继续写 |
| 临时文件清理 | 启动时清理上次遗留的 `.part` 文件 |
| 中断识别 | 启动时把停留在 `running` 的恢复操作标记为"部分完成/失败"，并告知用户可用安全点回滚 |

**从未出现的半写状态**：因为"先写临时文件、校验通过、再原子改名"是唯一的内容落盘路径。

## 5. 一致性与清理保护

历史清理时，**唯一不可删除的集合**是"被任何 `snapshot_files.object_id` 引用的对象"：

```sql
-- 清理保护名单（代码里用 ListReferencedObjectIds）
SELECT DISTINCT object_id FROM snapshot_files WHERE object_id IS NOT NULL;
```

于是：

- 自动清理只回收**没有被任何恢复点引用**的内容；
- 删除快照时才可能让某些对象失去引用（下一次清理回收）；
- **恢复点（基线 / 手动 / 恢复前安全点）默认不自动清理**；
- 因此"无论怎么清理，恢复到某个历史时间点的能力都不会失效"。

## 6. 时间表示

| 项 | 表示 | 理由 |
|---|---|---|
| 所有时刻 | `INTEGER`（UTC ticks） | 可排序、可索引、无时区歧义 |
| 落库时的本地时间 | 另存一列 `*_local` | **冻结显示**，避免事后系统时区变化导致时间线漂移 |
| 快照的本地时间 | 由 UTC **同一次取值**换算（`now.ToLocalTime()`） | 曾因两次独立取时钟导致毫秒错位、反查命中下一个快照（见 PIT-069） |

## 7. 已知取舍

| 取舍 | 说明 |
|---|---|
| 对象 Id 不稳定 | 内容索引重建后 Id 会重新分配。对外稳定的标识是**内容哈希**；上层每次都通过哈希解析 Id（`ContentResolver`），不长期持有 |
| 跨库无外键 | `objects.db` 与 `events.db` 分离，因此 `object_id` 的引用完整性由应用层保证（清理时用保护名单） |
| 清单行数随快照数增长 | N 个快照 × M 个文件 = N×M 行。当前规模（万级文件、百级快照）完全可控；若未来需要，可改为"只存差异 + 定期全量锚点" |
| 事件日志默认不自动删 | 事件是"事实"，默认长期保留；只有用户显式要求才按天数清理（恢复点不受影响） |
