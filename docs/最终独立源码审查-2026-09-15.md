审查日期：2026-09-15

审查角色：未参与开发的独立审查 Agent

## 1. 最终结论

**决定：暂不建议进入真实用户观察期。**

176/176 全绿是真实结果，但当前工作树仍存在会绕过恢复确认、错误恢复其他 root、经 junction 写出受保护根、并发串改恢复基线的 P0 路径；事件链还实际复现了 120ms 强制冲刷后吞第二次修改，以及 rename 未落库前紧接 delete 导致旧路径继续存活。它们与产品“可放心回到过去”的核心承诺直接冲突，不能降格为观察期小问题。

本结论不是说项目整体不可用。分层、增量清单 SQL、TypeChanged、rowid、时间范围 SQL、ObjectId 传播、cleanup 保护、Agent 基本进程协议等已有明显改善。但恢复工具的准入门槛不是“多数路径正确”，而是破坏性路径必须封闭；当前尚未达到。

## 2. 审查范围与证据等级

实际遍历：88 个 `*.cs`、8 个 `*.csproj`、1 个 `*.json`、8 个 `*.md`、1 个 `*.props`、3 个 `*.ps1`；没有 `*.targets`、`*.bat`。扫描了 solution、所有项目引用、生产代码、测试、协议与构建脚本。当前项目目录整体在父仓库中显示为 untracked，因此没有把 git diff 当证据。

证据标记：

- **实测**：本轮实际 clean/build/test 或独立探针复现。
- **源码确定性**：按当前代码，在给定调用序列下必然发生。
- **高可信风险**：竞态或系统条件相关，源码缺少必要保护，但本轮未命中运行窗口。
- **证据不足**：没有真实 GUI、跨进程或特定系统条件的运行证据。

## 3. 架构地图

真实项目依赖如下：

```text
Core
└─ 无项目依赖

Windows → Core
Data    → Core + Windows
Engine  → Core + Data + Windows
Runtime → Core + Data + Engine + Windows
App     → Runtime + Core + Data + Engine + Windows
Agent   → Runtime
```

结论：

- Agent 仍只引用 Runtime。
- Engine 没有引用 WPF 或 Agent；Core 没有被实现层反向污染。
- 没有项目循环依赖，没有 `PackageReference`，没有新增第三方 NuGet。
- solution 中仍是 8 个项目；`.offline` 下的临时性能/捕获工程不在 solution，不属于生产依赖。
- App 直接引用所有实现层，耦合较高但不是反向依赖或本轮阻断项。

```text
ReadDirectoryChangesW
→ DirectoryWatcher.ParseBuffer
→ RawFsNotification
→ WatchService.OnBatch / _inbox
→ EventMerger.Ingest / Advance / Flush
→ WatchEventPipeline.Persist
→ EventRepository.AppendRange
```

链路的主要问题不是末端前缀 SQL。`SnapshotRepository` 用精确相等加 `SUBSTR(prefix + '/')`，不会把 `%`、`_` 当 LIKE 通配符，也不会把 `A/B` 扩大到 `A/BB`。真正缺口在上游：删除后 `Directory.Exists` 无法识别已消失目录，而 EventMerger 没有按注释回查索引；另外强制 Flush 没有重置原始通知去重状态。

### FINAL-BB-001

等级：P0  
文件：`code/src/LastRegret.Core/Restore/RestorePlan.cs`；`code/src/LastRegret.Agent/AgentCommands.cs`  
类/方法：`RestorePlan.ComputeFingerprint`；`AgentCommands.ExecuteRestore`  
行：RestorePlan 124–137；AgentCommands 214–248  
调用链：CLI preview → 返回 fingerprint → 当前文件变化 → CLI restore → 重建计划 → fingerprint 比较 → RestoreEngine.Execute  
问题：指纹没有绑定 root、目标时间、目标快照和预览时的当前基线。  
为什么成立：指纹 key 只有 action/path/secondary/target hash/target object/kind，没有 `RootId`、`ExpectedCurrentHash` 或 `plan.Current`。只要目标动作不变，预览后文件再次变化，CLI 重建的新计划仍可得到同一指纹；执行引擎随后把“新计划的 Current”当作用户已确认基线。跨 root 内容与路径相同的计划也可同指纹。  
影响：用户确认的不是最终执行时所用的完整计划；未预览的新内容可被覆盖，形成恢复确认绕过。  
证据：实测旧 fingerprint 被接受并返回 `success`；本次具体时序被执行期 conflict 拦截，磁盘第三版未被覆盖。若新变化已被新进程索引捕获，源码确定会把新基线当成已确认基线，覆盖风险仍属高可信风险。  
是否旧问题回归：新增发现。  
建议：指纹至少绑定 root 身份、目标快照/时间、每步预期当前类型与 hash，并明确 preview token 的一次性/时效语义。

### FINAL-BB-002

等级：P0  
文件：`code/src/LastRegret.Core/Events/EventMerger.cs`；`code/src/LastRegret.Engine/SnapshotService.cs`  
类/方法：`EventMerger.HandleOne/Flush`；`SnapshotService.Create`  
行：EventMerger 153–166、194–210；SnapshotService 79–87  
调用链：modify A → Ingest 写 `_recent` → force flush → modify B（50ms）→ duplicate return → safety/manual snapshot  
问题：`Flush` 清空 pending/rename，却不清 `_recent`；强制边界后的第二次同动作真实变化仍被 120ms 去重。

建议：force flush 建立明确代际边界，重置/分代去重状态；安全快照的 flush 失败不得静默继续。

## 7. 恢复安全链逐项回答

1. preview 不直接改用户文件；但 CLI 创建 Runtime 会改 DB/store/监听状态，因此“进程零副作用”不成立。
2. fingerprint 没有绑定完整执行计划，尤其没绑定预览当前基线和 root，未通过。
3. fingerprint 可跨 root 相同，未通过。
4. Execute 会先建 safety snapshot；但并发/事件漏记可使其内容不是实际磁盘基线。
5. safety snapshot 抛错时会中止；但 SnapshotService 吞掉 FlushPending 异常后仍继续建点。
6. 当前文件缺安全内容时，BB-015 分支会按磁盘 File.Exists 拒绝，已修。
7. 执行期实际 hash 与基线不同会 skipped；CLI 重建计划会更新基线，削弱“自 preview 后变化”的含义。
8. skipped 已不计 FilesChanged。
9. `plan.HasEffect=false` 不建立 operation；全部 skipped 会建 operation，但 CanUndo=false。
10. partial failure 会记录 partial；单步 UpdateStep 异常被吞，审计可能不完整。
11. undo 指向 PreRestoreSnapshotId。
12. undo 本身创建新 restore operation，可再次 undo（表现为 redo），源码语义一致。
13. restore→restore→undo 默认撤销最近一次；显式 operationId 可选更早操作，但并发与 root 校验有缺口。
14. rowid 当前调用均位于同连接事务锁内；未发现现存串号点。
15.普通 restore 的 rootId 由 plan 获取；CLI undo 的 request rootId 与 operationId 没有归属校验。

## 9. 性能与低配置判断

- 1.5s cache、单 QueryObject worker、bounded queue=4、30s circuit、PID index、每次最多 3 个 name query 均不是报告口号，源码真实存在。
- 事件归属调用仍同步位于 Persist 中；最坏一次可阻塞约 1.2 秒，随后熔断。queue 满只丢 attribution，最终文件事件仍保存。
- attribution 的专职线程数量有界为 1；整个进程线程数并没有仅由该机制给出数学上界，每 root watcher、ThreadPool、WPF、测试线程都会增加。开发数据 35/79/173 不能证明“线程总数有界”，只能证明斜率大幅下降。
- 连续 burst 不会新建更多 QueryObject worker，但永久阻塞后 worker/queue 状态不会恢复；cache 是静态常驻直到进程退出，没有 Dispose。
- 本轮只实际跑了 150 事件归属用例（18 线程）。没有重跑 1000/5000/10000，也没有跑连续 5000×3，因此不对那些开发数字背书。
